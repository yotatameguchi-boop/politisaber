# PolitiSABER

日本の都道府県知事選の予測モデルと、その成績を正直に測るための計測系。

個人的な検証プロジェクトであり、公式な選挙予測ではありません。

---

## 何をするものか

3つの部分からなります。

1. **予測エンジン** — 得票率・投票総数・未モデル化候補を分けて確率的に予測する
2. **計測系** — 交差検証・スコアリング・較正。モデルが「本当はどれくらい当たるのか」を自己採点でなく外から測る
3. **表示** — 単一ファイルの HTML（`politisaber.html`）。ダブルクリックで開く

## ファイル構成

| ファイル | 役割 |
|---|---|
| `engine.js` | 予測エンジン本体。**唯一の実体**で、HTML と各スクリプトが共有する |
| `livecount.js` | 開票速報モデル（開票途中から最終結果を推定） |
| `template.html` | ページのひな形。データ（`RACES`）もここ |
| `build.js` | `engine.js` を `template.html` に差し込んで `politisaber.html` を生成 |
| `watch.js` | 保存を監視して自動ビルド |
| `backtest.js` | 係数推定・成績計測・交差検証（データは `politisaber.html` から読む） |
| `snapshot.js` | 予測を投開票前に凍結して `forecasts/` に保存 |
| `simcheck.js` | 開票速報モデルの検証（合成データ） |
| `server/store.js` | 開票途中経過の追記専用ストア（JSONL） |
| `server/pipeline.js` | 観測 → 開票速報の推定 |
| `server/sources/` | 取り込みアダプタ（CSV/JSON 手入力 ＋ スクレイパ雛形） |
| `server/api.js` | HTTP API（外部依存なし） |
| `server/cli.js` | 開票当日の操作口 |
| `server/test.js` | バックエンドの端から端までの検証（22件） |

## 使い方

```bash
node build.js      # politisaber.html を生成
node watch.js      # 保存を監視して自動ビルド
node backtest.js   # 係数推定と成績計測
node simcheck.js   # 開票速報モデルの検証
```

投開票前に予測を凍結する（較正を測るために必須）:

```bash
node snapshot.js
```

確定後に採点する:

```bash
node snapshot.js --verify
```

## 設計上の考え方

### 得票率は単体（合計100%の面）の上でサンプリングする

候補ごとに独立な区間を描くと、合計が100%を超える「存在しない領域」を示してしまいます。
実際、初期バージョンは長野で区間上限の合計が 120.4% になっていました。
ロジット正規（softmax）で単体上に乗せると、合計100%と候補間の負相関が構造的に保証されます。

### マージンと勝率は同時サンプルから直接数える

「区間の引き算」（`lo1 - hi2`）は、2候補の得票率が完全に連動することを無視した計算です。

### 投票率は独立の確率変数として分離する

得票率の誤差と投票率の誤差を票数の中で混ぜないため。
過去データでは投票総数を平均 +13.4% 過大に見積もる系統バイアスがあり、補正係数として組み込んでいます。

### 「予測に入れていなかった候補」に確率質量を置く

零過剰の混合分布（出現するか × 出現時の規模）として扱います。
ただしこれは保険であって免罪符ではありません。過去に 20.07% を得た候補は
**告示済みの登録候補**であり、統計以前に名簿を読めば防げた誤りでした。

### 自己採点を信用しない

係数を推定したのと同じデータで測ると必ず甘く出ます（実測: in-sample の被覆率 100%）。
`crossValidate()` が Leave-One-Out と walk-forward の両方を回します。
walk-forward は「それ以前のレースだけで学習する」実運用と同じ条件で、唯一完全に正直な評価です。

### 予測は投開票前に凍結する

`snapshot.js` は既存のスナップショットを**上書きしません**。
投開票後に予測を書き換えられると、較正もスコアも意味を失います。

## 初めて「凍結した予測」を採点できたレース

2026年8月9日の長野県知事選は、投開票前に `snapshot.js` で予測を凍結してあった最初のレースです。
後から書き換える余地がない記録との突き合わせなので、これが初めての正直な採点になります。

| | 予測（凍結時点） | 実際 | 誤差 |
|---|---|---|---|
| 阿部守一 | 84.6%（90%区間 70.8–93.8） | 86.13% | +1.54pt ✓区間内 |
| 武田良介 | 15.0%（90%区間 5.9–28.6） | 13.87% | −1.18pt ✓区間内 |
| 武田の得票数 | 92,571票 | 92,366票 | 205票 |
| 勝率 | 99.6%（阿部） | 阿部当選 | Brier 0.0000 |

**ただし投票総数は外しました。** 素の想定 693,617票に対し実際は 666,108票（+4.1%のズレ）でしたが、
過去5戦から推定した −11.4% の過大バイアス補正を掛けた結果 615,174票となり、**誤差が −7.6% に拡大**しました。
n=5 で推定した係数を6戦目に当てて裏目に出た形で、このプロジェクトが繰り返し警告している
「少数データから推定した係数を信用しすぎるな」の実例です。

6戦を反映した現在の係数: プール σ 4.55 → **4.18pt**、投票率バイアス補正 ×0.8859 → **×0.8979**。

## 開票速報モデル

合成データ（正解が分かっている世界、100試行）での実測:

| 開票率 | 90%区間の被覆率 | モデル誤差 | 素朴な按分 | 改善 |
|---|---|---|---|---|
| 10% | 90% | 0.86pt | 5.23pt | **6.1x** |
| 25% | 84% | 0.83pt | 3.69pt | 4.4x |
| 50% | 84% | 0.73pt | 2.14pt | 2.9x |
| 75% | 83% | 0.54pt | 0.84pt | 1.6x |
| 90% | 99% | 0.07pt | 0.10pt | 1.4x |

「素朴な按分」＝開いた分をそのまま全体に引き伸ばす方法。日本の開票は小規模自治体から
終わるため序盤は郡部に偏り、これだと大きく外れます。自治体ごとの過去の傾きを基準線にして
県全体のスイングを推定すると、**開票率10%の時点で誤差が6分の1**になります。

当確判定の閾値は 99.9%。当初 99.5% にしていたところ開票率10%時点で誤報が1件出たため
上げました（100試行で誤報ゼロを確認）。ただしこれは合成データに合わせた調整で、
実データでの再検証が要ります。

## バックエンド

開票速報だけは静的ページで完結しません。当日、市区町村別の途中経過が数時間にわたって
届き続けるので、取り込んで再計算する何かが要ります。

```bash
node server/cli.js init     okinawa2026        # レース定義の雛形
node server/cli.js ingest   okinawa2026 in.csv # 途中経過を取り込む
node server/cli.js estimate okinawa2026        # 現在の推定
node server/cli.js replay   okinawa2026        # 開票の進行に沿った推移
node server/api.js                             # HTTP API（既定 8787）
node server/test.js                            # 22件のテスト
```

**言語は Node です。Python にしていません。** モデルの実体（`engine.js` /
`livecount.js`）はブラウザとバックエンドで同じファイルを共有していて、Python にすると
モデルを二重実装することになります。このプロジェクトは既に2回、実体が複数あることが
原因のバグを出しているので（`toHistory` のフィールド落ち、`backtest.js` の HISTORY 重複）、
予測モデルでそれをやる判断はしませんでした。

Python が効くのは別の層です。構造モデル（提案4）や市区町村別の階層モデルの**係数推定**には
statsmodels / PyMC / scipy が明確に有利なので、そこは「Python でオフライン推定 → JSON で
係数を出力 → JS エンジンが読む」という分担が素直です。モデルの実装は1つのまま、
統計の重い部分だけ外に出せます。

### 設計上の要点

**観測は追記のみ。** 途中経過は何度も更新されるので、素直に実装すると上書きの連続になり
「何時の時点で何が分かっていたか」が失われます。`data/<raceId>.jsonl` に積むだけにして、
更新も削除もしません。これで任意の時刻断面を再構成でき（`estimate --asOf`）、訂正報道も
追え、書き換えによる捏造ができなくなります。

**スクレイパは同梱していません。** 実物のページ構造を確認せずに書いたスクレイパは、
動いているように見えて静かに誤った数字を入れます。このプロジェクトが最も避けたい失敗
そのものなので、アダプタの契約と検証だけ用意して、実装は実際のページを見てからにしてあります。
手入力の CSV/JSON アダプタは完成していて、1レースの開票当日はこれで回せます。

**取り込みは疑わしきを弾きます。** 候補者名がレース定義と違う、定義に無い自治体名、
非負整数でない得票数 — いずれもエラーにします。黙って 0 票として通すのが一番危険なので。

## 現状の限界

- **過去データが 6 レースしかありません。** すべての係数はこの規模から推定したもので、確定値ではありません。σ は交差検証で 2.8〜4.9pt と大きく振れます
- 90%区間の被覆率も候補12名分でしか測っていません。1名の増減で約8pt動く粒度です
- 未推定のまま無効化している係数があります（投票率の競争度、平均回帰λ、現職バイアス）
- 未モデル化候補は合計として扱うため、「想定外の候補が当選する」ケースは構造上表現できません
- 市区町村別の実データが無いため、開票速報モデルは合成データでの検証のみです（レース定義の `priorShares` を埋めるのが最大のボトルネック）
- スクレイピングのアダプタは未実装。開票当日は CSV の手入力で回す前提です
- 交差検証での90%区間の被覆率は 83〜90%（標準誤差 3.0pt）。わずかに過信気味です
- 全国共通ショックは総分散を保つよう σ から控除していますが、勝率という非線形量では
  厳密に相殺されず、個別レースの勝率が 1.6〜2.7pt 動きます（控除前は 2.6〜4.5pt）

**最も効くのは過去レースの収集です。** `template.html` の `RACES` に行を足すたび、
係数・較正・成績のすべてが自動で更新されます。47都道府県 × 直近数サイクルで
150〜200件を目標にすると、いま無効化している係数が推定できるようになります。
